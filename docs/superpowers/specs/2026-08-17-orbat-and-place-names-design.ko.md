# 편제(ORBAT) 도입과 통제점 지명화 — 설계

> 대상: `VR-Forces/` 파이프라인. 작성 2026-08-17.
> 관련: [README.md](../../../README.md) · [RUNBOOK.md](../../../RUNBOOK.md) ·
> STLogic 연구내용 §3.2(부대 = 구성원 중심점) · §3.3(분산 기반 자동 관련성 게이팅)

## 1. 왜 하는가

STKG가 연구용으로 성립하려면 두 가지가 빠져 있다.

**(1) 편제가 없다.** 지금 `roster.unit_of("FR-INF-001")`은 `"FR-INF"`를 준다. 이건
부대가 아니라 **진영+타입 접두사**다. `partOf`·`supports`·`reinforces`로 확장하려면
소대/중대/대대라는 실제 편제가 있어야 하고, **부대 자체가 주어인 fact**가 나와야 한다.

비교 대상인 백마고지 데이터셋을 전수 조사한 결과가 이 요구를 뒷받침한다
(75섹터 · 엔티티 5,131 · 변환 후 116,680행).

| | 값 |
|---|---:|
| 주어가 엔티티인 fact | 116,680 (100%) |
| **주어가 부대인 fact** | **0** |
| 목적어가 부대 | 47,050 |

부대는 목적어로만 존재한다. 우리 데이터셋은 여기를 메운다.

**(2) 지명이 `P1`~`P11`로 나간다.** 원본 CSV 실측:
`Move-To Waypoint: "P3"`. 시뮬레이터가 통제점의 `marking-text`를 그대로 내보내는데,
[writer.py:267](../../../vtmak/scnx/writer.py#L267)이 그 marking을 순번으로 찍는다.

```python
parts.append("  " + self._control_record(c, f"1:3001:{n}", f"P{k}"))
```

실측(ground_truth 20260809): `P2`·`P3`·`P4`·`P10`·`P11`이 **약 10.7만 행**. 전부 아군
객체다 — 적군은 좌표 이동이라 `locate.snap`이 `LOC_*`로 붙인다.

### 2.1 방향 전환 — 시뮬레이터 저작을 건드리지 않는다 (2026-08-18)

처음 설계는 부대를 `.oob`에 aggregate 객체로 저작하고 통제점 marking을 지명
코드로 바꾸는 것이었다. 구현해서 검증까지 마쳤으나(부대 67 · dangling 0 ·
사이클 없음 · 엔티티 328 전원 소속) **되돌렸다.**

바꾼 이유는 결함이 아니라 **비용**이다. 저작을 건드리면 시나리오를 다시 돌려야
하고, 그때마다 VR-Forces 로딩·성능·태스크 실행을 다시 확인해야 한다. 편제 관계와
지명 매핑은 둘 다 **관측 이후에 계산할 수 있는 것**이라 시뮬레이터를 위험에
빠뜨릴 이유가 없다.

바뀐 것과 안 바뀐 것:

| | 방식 |
|---|---|
| 편제 도출(`vtmak/orbat.py`·`config/orbat.json`) | 그대로 — 후처리가 쓴다 |
| 부대 사실 R8~R12(`derive/orbat_relations.py`) | 그대로 — 후처리 |
| 지명 복원(`stkg/rewrite.py`·`05`) | 그대로 — 후처리 |
| `.oob`의 부대 aggregate 67개 | **철회.** `.scnx`는 이전과 같은 형태(객체 347·aggregate 0) |
| 통제점 marking을 지명 코드로 | **철회.** marking은 `P{k}` 순번 그대로 |
| `04`의 통제점 대조표 | 유지하되 **`marking`(=`P{k}`) → `loc_id`** 로 키를 바꿈. `.scnx`에는 안 들어간다 |

그래서 §4(`.oob` 저작)와 §6.1의 marking 변경은 **구현하지 않는다.** 두 절은 그
방법이 실제로 되는지 확인한 기록으로 남긴다 — 나중에 저작 쪽으로 다시 갈 때
쓸 수 있다(3계층 aggregate가 실제로 닫힌다는 것은 §4.1에 실측으로 남아 있다).

### 왜 매 관측 복제를 하지 않는가

백마고지 데이터셋은 모든 관계를 매 관측마다 그대로 복제한다. 5,131 엔티티 중
**관계 집합이 한 번이라도 바뀐 엔티티가 0개**(0.00%)다. 위치는 100% 변하는데
관계는 t0에 정해져 10회 관측에 복사된다.

결과로 고유 `(s,r,o)` 쌍 11,668개가 각각 정확히 10개 타임스탬프를 갖는다.
split은 섹터 단위라 train/test 누출은 0%로 깨끗하지만, **split 안**이 문제다 —
test 20,210행 중 첫 등장은 2,021행뿐이고 **18,189행(90%)이 앞 시각에 같은 fact가
이미 있는 반복**이다. "직전에 본 fact를 다시 낸다"는 규칙 하나로 test의 90%를 맞춘다.

STLogic의 핵심 주장은 "한 시간 규칙이 만든 다수 후보를 공간으로 변별한다"인데,
후보가 갈릴 일이 없으면 그 주장이 작동할 자리가 없다. 새 데이터셋에서 이걸
반복하지 않는다.

### 3.2 도출 규칙

원문 1,294줄에 소대·중대·대대 언급이 **0건**이라 편제는 추출이 아니라 저작이다.
그런데 `(진영 × 역할 × 초기 배치 지명)`으로 이미 30개 역할군이 깔끔하게 나온다.
여기에 축약 정원만 얹어 결정적으로 분할한다.

1. 역할군을 `function_of_role`로 **기능**에 매핑한다.
2. 같은 기능·같은 진영의 역할군을 모아 **중대**를 만든다. 전차는 진지(능선)별로 나눈다.
3. 각 역할군을 `platoon_capacity`로 나눠 **소대**를 만든다.
4. 소대가 1개뿐인 기능(대전차·정찰·방공·본부)은 중대를 만들지 않고 **대대 직할**로 단다.
5. 보병처럼 소대가 3개를 넘으면 `platoons_per_company`로 중대를 나눈다.

난수도 해시도 쓰지 않는다. 정렬된 목록의 순서가 편성을 정한다 —
`placement.py`가 이미 쓰는 규칙과 같다.

**대대 2 · 중대 13 · 소대 52 = 부대 객체 67개** (엔티티 328은 그대로).

체인 깊이가 섞인다. `보병 → 소대 → 중대 → 대대`(3단)와 `ZPU → 방공소대 → 대대`(2단)가

전이 길이가 다른 예제를 준다.

**방공은 화력이 아니라 전투지원**으로 본다. 3문짜리 독립 방공대대는 규모상 과장이고,
방공은 상위 기동부대의 organic 능력으로 보는 편이 맞다.

### 3.4 지원관계 (`task_organization`) 초안

`supports`·`reinforces`는 원문에 근거가 없어 저작한다. 실제 OPORD가 화력을
"직접지원(DS)"으로 배속하는 방식을 따라 **중대 단위**로 건다. 초안은 다음과 같고
`orbat.json`에서 손으로 고친다.

| 진영 | 관계 | 주체 | 대상 |
|---|---|---|---|
| FR | `supports` | 화력중대 | 보병중대 |
| FR | `supports` | 대전차 1소대 | 보병중대 |
| FR | `reinforces` | 전차중대(서측능선) | 보병중대 |
| FR | `supports` | 군수중대 | 대대 |
| EN | `supports` | 화력중대 | 보병중대 1 |
| EN | `reinforces` | 전차중대(접근로) | 보병중대 1 |
| EN | `reinforces` | 전차중대(예비) | 보병중대 2 |
| EN | `supports` | 군수중대 | 대대 |

이 8건은 편제표에 선언된 값이지 관측에서 파생된 값이 아니다. 산출물에서 그 구분이
사라지지 않도록 파생 레이어의 `layer` 필드로 표시한다(`derive/relations.py`의
`LAYER = "derived"`와 같은 자리).

### 3.5 ID·표기

DIS `marking-text`가 11바이트라 한글이 안 들어간다. 한글 이름은 `object-label`에 둔다.

나열하면 객체 수가 바뀔 때마다 어긋난다.

## 4. `.oob`에 부대 객체 저작 — **철회됨(§2.1)**

> 아래는 구현·검증까지 마친 뒤 되돌린 방식이다. 실행하지 않는다.
> 되는지 확인한 기록으로 남긴다.

### 4.1 실측 — 3계층 중첩이 된다

2026-08-17 갱신된 골든 `yewon_test/yewon_test.oob`(944KB)에 GUI로 저작한 3계층
조직 트리가 들어왔다. 코드로 검증한 결과:

```
대대 443ec843   parent="VRF_UUID:1 Force"   subordinate-of-force-level True
├─ 중대 1 f988981f  parent=대대   sofl=False   ├─ 소대 1(엔티티 2) └─ 소대 2(엔티티 3)
└─ 중대 2 2177f0b5  parent=대대   sofl=False   ├─ 소대 3(엔티티 3) └─ 소대 4(엔티티 2)
```

- aggregate 7 · local-vrf-object 53 = 객체 60
- 해석 안 되는 `parent-name` **0건** · 사이클 **없음** · 깊이 1~4
- `.omp` 항목 60 = `.oob` 객체 60 (양쪽 다 빠짐 0)
- 부대 DIS 타입은 제대와 무관하게 전부 `object-type 3 (11 1 0 0 34 0 11)`.
  제대는 타입이 아니라 이름과 트리로만 구분된다.
- 부대에만 있는 필드 3개: `(formation "Other")` · `(formation-name "")` ·
  `(aggregate-state Disaggregated)`
- `DtDoNotAddToOrbat "1"`은 지형점·엔티티·부대 **전 객체**에 붙어 있다. ORBAT 표시를
  막는 값이 아니라 기본값이다. 골든 그대로 복제한다.

기존 골든 통제점 23개는 그대로다. 테스트 319 통과(실패 1건은 골든 교체 이전부터
있던 `test_gimbal_is_rewritten_in_the_cloned_record`).

### 4.2 바꿀 곳

1. **`golden.py`** — `_parse_objects`가 `(local-vrf-object`만 읽어 aggregate를 못 본다.
   `(aggregate` 레코드를 잘라내는 `aggregate_templates()`를 추가한다. 이제 골든에
   대대·중대·소대 실제 레코드가 다 있으므로 제대별 템플릿을 그대로 뜬다.
2. **`spec.py`** — `UnitSpec(unit_id, name, marking, uuid, echelon, faction, parent,
   members, coord)`. **부대 좌표 = 구성원 배치 좌표의 중심점.**
3. **`writer._oob`** — 대대 → 중대 → 소대 → 엔티티 순으로 내보내고 `parent-name`
   체인을 잇는다. 엔티티의 `parent-name`이 지금은 force 루트로 강제되는데
   ([writer.py:232](../../../vtmak/scnx/writer.py#L232)) 소속 소대 uuid로 바뀐다.
   대대만 `subordinate-of-force-level True`, 나머지는 `False`.
4. **`writer._omp`** — 부대 uuid를 주소맵에 넣는다. 여기 없는 객체는 로드돼도
   나타나지 않는다.
5. **엔티티 태스크는 건드리지 않는다.** 328개 개별 `.pln`이 그대로 간다. 골든에서
   `Truck 1`(소대 2 예하)·`T-72 1`(소대 4 예하)이 `independently-tasked False`인데도
   자기 uuid로 된 개별 Plan을 갖고 있고, 예하 객체가 각자 플랜대로 움직이는 것은
   연구자가 VR-Forces에서 확인했다. **부대 단위 태스크는 만들지 않는다.**

기존 `_check_org_tree`가 그대로 무한 로딩을 막는다. 부대를 같은 파일에 선언하므로
dangling이 생기지 않는다.

## 5. 부대 사실 파생 — `vtmak/derive/`

시뮬레이터가 aggregate를 CSV로 내보내는지는 확인하지 않았고, **확인할 필요도 없다.**
부대 fact는 후처리에서 만든다. 그래야 내보내기 판이 바뀌어도 결과가 같다.

`vtmak/derive/`는 이미 R1~R7을 같은 방식으로 만든다. 특히 **R5가 "부대 → 구성원" 표를,
R6가 "부대가 제압됐다"를 부대 주체로** 내고 있다. `unit_of()`가 주는 값을 타입 접두사
(`FR-INF`)에서 `orbat.json`이 정한 소대로 바꾸면 R5·R6가 자동으로 진짜 편제 기준이 된다.

| 관계 | 주체 | 근거 |
|---|---|---|
| `partOf` | 엔티티→소대, 소대→중대, 중대→대대 | 편제표 (2단계 전이 체인) |
| `movesToward` | **부대**→지명 | 구성원 과반이 같은 지명으로 이동 중 |
| `occupies` | **부대**→지명 | 부대 중심점이 그 지명 반경 안 |
| `firesUpon` | **부대**→부대/지명 | 구성원 다수가 같은 대상 사격 |
| `unitSuppressed` | **부대** | 기존 R6 (임계 0.25) |
| `supports` / `reinforces` | 중대→중대 | 편제표의 `task_organization` |

임계값(과반 비율·지명 반경)은 R6의 `suppressed_ratio`와 같이 **`derive_rules.csv`에 두고
실측으로 정한다.** 코드에 박지 않는다 — 값을 바꾸면 몇 건이 되는지가 근거다.

**시간축**: 위치에서 파생되는 관계(`movesToward`·`occupies`·`firesUpon`)는 부대 중심점이
실제로 움직이므로 자연히 시변한다. `partOf`·`supports`·`reinforces`는 **t0에 한 번 내고
이후 실제로 바뀔 때만** 낸다.

**빈 구멍**: `vtmak/derive/`는 지금 어느 스크립트도 호출하지 않는 라이브러리다
(테스트만 있다). 파생 결과를 산출물로 내려면 스크립트가 필요하다 —
`07_derive_relations.py` 신설과 `06_evaluate_dataset.py` 확장 중 구현 때 정한다.
